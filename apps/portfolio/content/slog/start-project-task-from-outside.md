目的は、Claudeプロジェクトに属するスケジュールタスクをClaudeの外から、1回の呼び出しでポーリングなしに起動することだった。呼び出し元はMCPツールの `send_to_claude` で、依頼の中身をプロジェクトに届ける必要がある。本ノートでは、公開APIが今どう動くか、どこで壊れるか、その周りに何を作ったかを記録する。事実は2026年11月27日に確認した。

## APIはタスクを起動し、ボディは任意である

スケジュールタスクは最近までルーティンと呼ばれていた。その名前はAPIのパスに残っている。APIトリガーを付けられるのはWeb UIだけである。タスクを開いて編集し、トリガーを追加してトークンを作る。CLIからは作れず、トークンを管理するAPIもない。トークンは1度しか表示されず、そのタスク1つだけを起動でき、ほかの操作はできない[^routines-fire]。

[fire エンドポイント](https://platform.claude.com/docs/en/api/claude-code/routines-fire)は `POST https://api.anthropic.com/v1/claude_code/routines/{trigger_id}/fire` である。トークンはBearerで送り、`anthropic-version` ヘッダーを付ける。ボディは任意で、フィールドは `text` だけである。最大65,536文字の自由なテキストで、タスクはこれを信頼できない文脈として受け取る。成功すると、実行の終了を待たずにセッションが作られた時点でセッションIDとURLが返る。このAPIは実験的と明記されている。

呼び出す側には次の制限が効く。

| 制限                 | 値                                          |
| -------------------- | ------------------------------------------- |
| タスクごとの起動     | 1時間に30回。「Run now」ボタンと共有する    |
| アカウントごとの起動 | 1時間に100回。全タスクの合計                |
| 冪等キー             | なし。再試行すると2つ目のセッションができる |
| ステータス400        | `anthropic-version` がないときにも返る      |

## プロジェクトのタスクはボディをすべて拒否する

私たちのタスクはClaudeプロジェクトの中にあり、そこでは文書どおりの呼び出しが失敗する。`{"text": "..."}` を付けて起動すると、プロジェクトは動いていて「Run now」も通るのに、`403 permission_error` と `this project is paused` が返る。ボディなしか `{}` で同じ呼び出しをすると200が返り、セッションが始まる。プロジェクトの外にあるタスクは、`text` を普通に受け付ける。

これは [anthropics/claude-code#102874](https://github.com/anthropics/claude-code/issues/102874) で、10月16日に立ち、11月27日もオープンのままである[^issue-102874]。何人もが再現しているが、メンテナーの返信はない。11月10日に作ったプロジェクトでは `text` が通ったという報告があり、プロジェクトの作成日が条件だと見る向きもある。だが別の報告はこれと食い違う。外からは原因を直せないので、設計はボディが届かない前提で組んだ。

## 依頼の中身はキューを通す

中身は別の道で運ぶ必要がある。そこでMCPツールは仕事を2つに分けた。

1. `send_to_claude` が依頼をD1のテーブルに書き、空のボディでタスクを起動する。ツールは依頼のIDと、起動できたかどうかを返す。
2. 始まったセッションが `take_claude_requests` で未取得の依頼をすべて取り、処理して、1件ずつ `reply_to_request` で答える。送り手は `list_claude_replies` で答えを読む。

ツールは起動した時点では依頼を取得済みにしない。そのため起動に失敗しても何も失われない。依頼はキューに残り、次に始まったセッションが取る。起動はタスクのトークンを持つブローカーのWorkerが行う。トークンは1度だけ登録する。リポジトリとプロンプトには現れない。

## 途中でうまくいかなかったこと

起動が使えるようになる前は、毎時のタスクがキューをポーリングしていた。APIが動き出してもそのタスクが残り、依頼を処理し続けた。APIトリガーを付けたタスクはUIに「まだ実行されていません」と出たままで、APIが何もしていないように見えた。テストの依頼に答えた12:44 UTCの実行は、この毎時のタスクのものだった。これを削除し、今はAPIトリガーのタスクだけが経路になっている。

実際の依頼で確かめた。13:37 UTCに送ったテストは `fired` を返し、タスクの最終実行は13:37:23 UTCに `SUCCEEDED` と表示され、依頼の本文はキューを通って調整役のセッションに届いた。

## バグが直ったらどうするか

キューは1つのバグを避けるための回り道である。プロジェクトの中でも `text` が通るようになれば、依頼の本文を起動の呼び出しに直接載せられる。そのときキューは依頼と答えの記録に縮む。それまでは、何も載せずに起動して、始まったセッションに仕事を取りに行かせる設計が安全である。

masseater.dev は、オーナーがビルドするほぼすべての内容を保持するモノレポである。本ノートでは、11月27日の計測値をもとに、これまでに問題となった点をまとめている。これまでのノートでは、[CIキャッシュ](/slog/monorepo-ci-cache)、[CIが低速化した原因](/slog/monorepo-ci-slowness)、および[リポジトリのサイズ](/slog/monorepo-size)について、個別の原因を詳細に解説している。

## アクションキャッシュはすべてで共有される

GitHub Actionsはリポジトリごとに10GBのキャッシュを保持し、それを超えると最も長く使われていないエントリから追い出す。このリポジトリは11月25日に10.3GBに達した。日次プルーニング直後でも依然として6.5GBとなっており、以下の3つの要因がこれを占めている。

| 何が                 | サイズ                  | なぜ増えるか                                         |
| -------------------- | ----------------------- | ---------------------------------------------------- |
| pnpm ストア          | 2.1 GB                  | ロックファイルが変わるたびに新しいコピーが保存される |
| Vite Task キャッシュ | プッシュごとに約0.75 GB | 6つの verify シャードがそれぞれ自分の分を保存する    |
| sccache のエントリ   | 約3,700件               | プルーニングでは届かない                             |

復元も無料ではない。キャッシュの展開には1回あたり約60秒かかり、その時間はダウンロードではなく解凍に費やされるため、ネットワークが高速であっても意味がない。

## クラウドセッションでは、チェックを並列に実行できない

クラウドセッションは16GBのRAMを搭載しており、そのうち約14.3GBが利用可能で、スワップはない。単一のステップだけで、すでにその大部分を占めている。`vp check`内の3つのプロセスは最大7.2、3.2、2.4GBに達し、ステップ全体では最大約10.5GBとなる。

| ステップ                                 | ピーク時のメモリ |
| ---------------------------------------- | ---------------- |
| `vp check`（ステップ全体）               | 約10.5 GB        |
| `vp check`: tsgolint                     | 7.2 GB           |
| `vp check`: 型付きルール用の `tsc --api` | 3.2 GB           |
| `vp check`: oxlint                       | 2.4 GB           |
| msch                                     | 6.4 GB           |
| テスト                                   | 4 GB             |

Cargo、fallow、Chromeは、これらに隣接して起動するとメモリ不足に陥る。解決策は一度に1つのタスクを実行することであり、これによりコールド検証に約20分かかる。プリプッシュフックは同じ検証をするため、プッシュするたびにそのコストが発生する。

型付きリントは、リポジトリ全体に対して1つのTypeScriptプログラムを構築する。そのため、パッケージ数が増えるにつれてメモリが増大する。

## シャーディングしても検証は速くならない

CIでは、6つのシャードで動作しているにもかかわらず、検証に依然として15分ほどかかる。作業を細分化しても、その時間は短縮されていない。

## 類似のコードは1つのリポジトリ内でのみ見える

リポジトリを分割すると、類似コードチェックで同一リポジトリ内の関数を比較するため、本来共有されるべきコードが隠されてしまう。[fallow similar-code](/slog/fallow-similar-code)では、リポジトリをまたいだチェックを専用に構築する必要がある。fallowは1回の実行につき1,414個の関数で停止するため、比較はシャーディングする必要がある。

これが、全体をまとめ上げる最大の根拠となる。誤った分割は、どちらの側からも見抜けない。

## 分割における意味

デフォルトは1つのリポジトリである。分割するのは、2つの条件がそろった場合に限る。すなわち、まとめて置いても得るものがなく、安定していて隣接する部分と何も共有しない場合で、かつ前述のコストが実際に負担となる場合である。フォークが容易であることも理由の1つになり得るが、それだけでは不十分だ。分割する際、定期的なリポジトリ間の類似コードチェックが、誤った分割を可視化する安全策となる。

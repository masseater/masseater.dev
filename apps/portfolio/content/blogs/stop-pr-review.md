この一週間で masseater.dev の main には 97 本の PR が入った。書いたのは Claude か Renovate で、僕は差分を読まずにマージさせている。リポジトリの AGENTS.md には「PR のレビュー、PR ごとの CI・動作検証・デプロイはしない。動作は本番で確かめる」と書いてあり、Claude は手元の verify が通れば自分でマージする。マージしてよいかも聞かない。

やめる前に、そもそも PR レビューで何を担保していたのかを考えた。バグを本番に出さないこと、書いた人以外がコードを知ること、命名や設計がほかとずれないこと、そして誰かが見たという安心が思い当たる。どれもレビューでは中途半端にしか担保できていなかった。レビューを通ったバグは本番で見つかる。レビューした人も自分が読んだ差分しか知らず、プロダクトの全体像を常に 100% 把握し切っている人なんてこれまでも存在しなかった。ずれは気づいた人が気づいた範囲で指摘するだけで、安心は品質ではない。

それで済んでいたのは、開発が現実にそこまで速くなかったからである。本来やるべきことは、関わる全員が責任を持ち本番で動くかを確かめ、検査を機械に任せて速く出しリターンを取ることだった。人が書く速さなら PR を人が読むだけで回ってしまい、全部サボれていた。レビューは、やるべきことをやらずに済ませるための形だった。

Claude が 1 日に数十本の PR を書く今はサボれない。変更は人が読み終わるまで main に入らず、Claude がどれだけ速く書いても人が読む速さまでしか進まない。レビューは壊れるリスクを減らす代わりに、速く出せば得られるリターンを捨てている。人をボトルネックにしてリターンを捨てる運用を、事業会社が許容してはいけない。リスクとリターンのうちリターンをちゃんと取ったほうがいい。

「承認ボタンを押した人が責任を取る」という建前にも意味を感じていない。壊れたときはプロダクトに関わる全員で直すのであって、承認した一人だけが直すわけではない。Claude が書くようになってもそこは変わらない。

だから PR ごとの検査はやめ、main へマージしてから本番で動くかを確かめている。残すべきなのはどう作るかの意図と制約で、僕はそれを AGENTS.md と lint のルールに書き、Claude はそれを読んでから書く。この一週間で 97 本入れて、vite-plus の更新 1 本を戻した。

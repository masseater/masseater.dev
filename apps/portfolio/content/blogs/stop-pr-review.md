僕のリポジトリでは PR のレビューをしていない。AGENTS.md には「PR のレビュー、PR ごとの CI・動作検証・デプロイはしない。動作は本番で確かめる」と書いてあり、Claude は変更を書いたら手元の verify を通して自分で main にマージする。マージしてよいかも聞かせていない。人に話すとたいてい顔をしかめられるので、なぜそうしているのかを書いておく。

## レビューが担保していたもの

やめる前に、PR レビューがそもそも何を担保していたのかを考えた。僕の答えは 2 つで、高価なコードの事故防止と、書いた人以外がコードを知ることである。

事故防止のほうは「コードを書くのが高く、直すのも高い」という前提に立っている。人が何日もかけて書いた変更が壊れていたら、気づくのは本番で、直すのにまた何日もかかる。だから壊れる前に、もう一人の人間の目で止める。PR レビューはコードが高価だった時代の保険であった。

知ることのほうは、コードを書いた人の頭の中にしかない判断を、ほかの人の頭にも移すための場だった。差分を読み、なぜこう書いたかを尋ね、答えを聞いて、その人が辞めてもコードが読めるようにする。この共有はコードを書くのが人間である限り必要で、差分を読む以外にやりようもなかった。

## 前提が変わった

今年になって、どちらの前提も崩れた。変更を書くのは AI で、数分で PR ができる。壊れていたら revert するか、もう一度頼めばよく、直すのにも数分しかかからない。一方で、人が差分を読む時間だけは安くなっていない。1 日に何本も PR が出てくる状況で全部を読むことはできず、読んだふりをして承認ボタンを押すのは、読まないよりも悪い。壊れたときの損害が、人が読む手間より安くなった時点で、マージ前に人が止める意味はなくなった。

共有すべき知識も、差分ではなくなった。人がコードを書かなくなった今、書いた人の頭の中にあるものは存在せず、代わりにあるのは、どう作るかの意図と制約である。僕はレビューで繰り返し言っていたことを AGENTS.md と lint のルールに書き、AI はそれを読んで書く。レビューのコメントは、一度書けば次から機械が守らせる規則になり、人から人へ口で伝える必要がなくなった。

## 今の運用

だから僕は PR 単位での検査をやめ、main にマージしてから統合された状態を確かめている。PR で検査しているのはそのブランチだけの仮の状態で、僕が本当に知りたいのは main が動くかどうかである。本番で壊れていれば戻す。方針に合わない変更をマージしてしまったこともあるが、戻すのにかかったのは Claude への一言だった。

承認ボタンが「誰かが責任を取った」という形式を残すことには、価値を感じていない。責任は PR 単位で誰かが持つものではなく、プロダクトに関わる全員が持つものだと思っている。誰が承認したかを記録に残しても、本番で壊れたときに直すのは結局その全員である。

人に残ったのは、何を作るかと、どの方向に進めるかを決断することだけである。それは差分を読んでも分からず、レビューが担保してくれたこともなかった。コードが高かった時代の習慣に、安くなった今も同じ時間を払い続ける理由を、僕は見つけられていない。

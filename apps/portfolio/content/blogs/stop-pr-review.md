この一週間で masseater.dev の main には 97 本の PR が入った。書いたのは Claude か Renovate で、僕は差分を読まずにマージさせている。リポジトリの AGENTS.md には「PR のレビュー、PR ごとの CI・動作検証・デプロイはしない。動作は本番で確かめる」と書いてあり、Claude は手元の verify が通れば自分でマージする。マージしてよいかも聞かない。

やめる前にそもそも PR レビューで何を担保していたのかを考えた。高いコードを壊さないことと、書いた人以外がコードを知ることの 2 つだと僕は考えている。

人が何日もかけて書いた変更が壊れていれば、直すのにまた何日もかかる。だからマージの前にもう一人が読んで止めていた。今は Claude が数分で PR を書き、壊れていれば revert するか頼み直せば数分で終わる。人が PR を読む時間だけは速くなっていない。

「書いた人以外がコードを知る」のほうは元から怪しい。プロダクトの全体像を常に 100% 把握し切っている人なんて、これまでも存在しなかった。レビューした人も自分が読んだ差分しか知らず、読まなかった場所は知らないままである。人がコードを書かない今、ほかの人にはどう作るかの意図と制約を残せばよく、僕はそれを AGENTS.md と lint のルールに書いている。Claude はそれを読んでから書く。

担保していたものはこの程度である。それでもレビューを挟むと、変更は人が読み終わるまで main に入らない。Claude がどれだけ速く書いても、人が読む速さまでしか進まない。レビューは壊れるリスクを減らす代わりに、速く出せば得られるリターンを捨てている。人をボトルネックにしてリターンを捨てる運用を、事業会社が許容してはいけない。リスクとリターンのうちリターンをちゃんと取ったほうがいい。

「承認ボタンを押した人が責任を取る」という建前にも意味を感じていない。壊れたときはプロダクトに関わる全員で直すのであって、承認した一人だけが直すわけではない。Claude が書くようになってもそこは変わらない。

だから PR ごとの検査はやめ、main へマージしてから本番で動くかを確かめている。この一週間で 97 本入れて、vite-plus の更新 1 本を戻した。

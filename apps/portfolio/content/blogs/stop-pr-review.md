僕のリポジトリでは PR のレビューをしていない。Claude が変更を書き、手元の verify を通して自分で main にマージする。マージしてよいかも聞かせていない。動くかどうかは本番で確かめる。

やめる前に、そもそも PR レビューで何を担保していたのかを考えた。僕の答えは 2 つで、高いコードが壊れないようにすることと、書いた人以外がコードを知ることだ。

1 つめは、人がコードを書いていたから必要だった。人が何日もかけて書いた変更が壊れていれば、直すのにまた何日もかかる。だからマージする前にもう一人が読んで止めていた。今はコードを書くのは Claude で、PR は数分でできる。壊れていれば revert するか、もう一度頼めばよく、それも数分で終わる。何日もかかる作業は、人が PR を読むことだけになった。

2 つめはもっと怪しい。差分を読んでなぜこう書いたかを尋ね、書いた人が辞めてもほかの人がコードを読めるようにする。そう言われてきたが、プロダクトの全体像を常に 100% 把握し切っている人なんてこれまでも存在しなかった。レビューした人が知っているのは自分が読んだ差分だけで、それ以外の場所はレビューしても知らないままだった。人がコードを書かなくなった今、ほかの人に伝えるべきなのはどう作るかの意図と制約で、僕はそれを AGENTS.md と lint のルールに書いている。Claude はそれを読んで書く。

担保していたものがこの程度なのに、レビューをすると変更は人が読み終わるまで main に入らない。Claude がどれだけ速く書いても、人が読む速さまでしか進まない。事業会社がこれを許容してはいけない。レビューは壊れるリスクを減らす代わりに、速く出すことで得られるリターンを捨てている。リスクとリターンのうちリターンをちゃんと取るなら、人を待たずにマージするしかない。

承認ボタンを押した人が責任を取る、という決まりにも意味を見いだしていない。壊れたら直すのは PR を承認した一人ではなく、プロダクトに関わる全員だ。これは Claude が書くようになっても変わらない。

だから PR ごとに検査するのはやめて、main にマージしてから本番で動くかを確かめている。PR の時点で動いても、知りたいのは main が動くかどうかだ。本番で壊れていれば戻す。方針に合わない変更をマージしてしまったこともあるが、戻すのにかかったのは Claude への一言だった。

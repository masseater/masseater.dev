僕のリポジトリでは PR のレビューをしていない。AGENTS.md には「PR のレビュー、PR ごとの CI・動作検証・デプロイはしない。動作は本番で確かめる」と書いてあり、Claude は変更を書いたら手元の verify を通して自分で main にマージする。マージしてよいかも聞かせていない。人に話すとたいてい顔をしかめられるので、なぜそうしているのかを書いておく。

## レビューが担保していたもの

やめる前に、PR レビューがそもそも何を担保していたのかを考えた。バグを見つける、規約をそろえる、書いた人以外がコードを知るといった答えはどれも正しい。ただしそれらの底にあるのは「コードを書くのが高く、直すのも高い」という前提である。人が何日もかけて書いた変更が壊れていたら、気づくのは本番で、直すのにまた何日もかかる。だから壊れる前に、もう一人の人間の目で止める。PR レビューはコードが高価だった時代の事故防止であり、僕はそう理解している。

実際に僕がレビューで指摘してきたことを思い返すと、「名前が悪い」「null の確認が抜けている」「規約から外れている」「この設計は後で困る」の 4 種類にほぼ収まる。前の 3 つは lint と型とテストで検出できる。僕のリポジトリでは新しい lint のルールを足したら違反はコード側で直すことにしていて、ルールを off にして逃げることは禁じている。レビューで人が言っていたことは、ルールにできるものから順に verify へ移っていった。

## 前提が変わった

その前提が今年になって崩れた。変更を書くのは AI で、数分で PR ができる。壊れていたら revert するか、もう一度頼めばよく、直すのにも数分しかかからない。一方で、人が差分を読む時間だけは安くなっていない。1 日に何本も PR が出てくる状況で全部を読むことはできず、読んだふりをして承認ボタンを押すのは、読まないよりも悪い。壊れたときの損害が、人が読む手間より安くなった時点で、マージ前に人が止める意味はなくなった。

だから僕は PR 単位での検査をやめ、main にマージしてから統合された状態を確かめている。PR で検査しているのはそのブランチだけの仮の状態で、僕が本当に知りたいのは main が動くかどうかである。本番で壊れていれば戻す。方針に合わない変更をマージしてしまったこともあるが、戻すのにかかったのは Claude への一言だった。

## 残ったもの

レビューが担っていた知識の共有も、形を変えて残っている。人がコードを書かなくなった今、共有すべきなのは差分ではなく、どう作るかの意図と制約だ。レビューで繰り返し言っていたことは AGENTS.md と lint のルールに書き、AI はそれを読んで書く。レビューのコメントは、一度書けば次から機械が守らせる規則になった。

人に残ったのは、何を作るかと、どの方向に進めるかを決断することだけである。それは差分を読んでも分からず、レビューが担保してくれたこともなかった。コードが高かった時代の習慣に、安くなった今も同じ時間を払い続ける理由を、僕は見つけられていない。

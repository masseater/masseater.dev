僕のリポジトリでは PR のレビューをしていない。AGENTS.md には「PR のレビュー、PR ごとの CI・動作検証・デプロイはしない。動作は本番で確かめる」と書いてあり、Claude は変更を書いたら手元の verify を通して自分で main にマージする。マージしてよいかも聞かせていない。

## レビューが担保していたもの

やめる前に PR レビューがそもそも何を担保していたのかを考えた。僕の答えは 2 つある。高価なコードの事故防止と、書いた人以外がコードを知ることである。

事故防止は「コードを書くのが高く、直すのも高い」という前提に立っていた。人が何日もかけて書いた変更が壊れていれば本番で気づき、直すのにまた何日もかかる。だから壊れる前にもう一人の人間が読んで止めていた。

知ることのほうは、書いた人の頭の中にしかない判断をほかの人の頭にも移す場だった。差分を読んでなぜこう書いたかを尋ね、その人が辞めてもコードを読める状態を保つ。人がコードを書く限りこの共有は必要で、差分を読む以外にやりようもなかった。もっとも、プロダクトの全体像を常に 100% 把握している人はこれまでも存在しなかったので、レビューが担保していた共有は最初から部分的なものである。

## 前提が変わった

今年になってどちらの前提も崩れた。変更を書くのは AI で、数分で PR ができる。壊れていれば revert するか、もう一度頼めばよく、直すのにも数分しかかからない。壊れたときの損害は人が読む手間より安くなり、マージ前に人が止める理由はなくなった。

共有すべき知識も差分ではなくなった。人がコードを書かなくなった今、残すべきなのはどう作るかの意図と制約である。僕はレビューで繰り返し言っていたことを AGENTS.md と lint のルールに書き、AI はそれを読んで書く。一度書いた規則は次の変更にも適用され、人から人へ口で伝える必要がない。

## リターンを取る

レビューはリスクを抑える手段であり、その代わりにリターンを捨てている。PR を人が読む運用では、変更を書く速さをどれだけ上げても人が読む速さまでしか進めない。レビューする人がボトルネックになる状態を事業会社は許容してはいけない。リスクとリターンのうちリターンをちゃんと取るなら、人を待たずにマージするしかない。

承認ボタンが「誰かが責任を取った」という形式を残すことにも意味を見いだしていない。責任は PR 単位で誰かが持つものではなく、プロダクトに関わる全員が持つものである。これは AI が書くようになっても変わらない。

## 今の運用

だから僕は PR 単位での検査をやめ、main にマージしてから統合された状態を確かめている。PR で検査できるのはそのブランチだけの仮の状態で、僕が知りたいのは main が動くかどうかだ。本番で壊れていれば戻す。方針に合わない変更をマージしてしまったこともあるが、戻すのにかかったのは Claude への一言だった。

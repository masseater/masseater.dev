[@r_masseater/vitest-otlp](https://www.npmjs.com/package/@r_masseater/vitest-otlp) is a Vitest plugin that receives OTLP during tests. A test can then assert on the spans, log records and metrics that the code under test really exported over the network. Such a test also shows that auto-instrumentation and the `OTEL_*` environment variables work, which a test against an in-memory exporter cannot show. The version described here is 0.2.0, and it requires [Vite+](https://viteplus.dev/) and Node.js 26 or later.

```ts
import { otlp } from "@r_masseater/vitest-otlp";
import { defineConfig } from "vite-plus";

export default defineConfig({
  plugins: [otlp()],
});
```

## Each test file gets its own receiver

The plugin adds a setup file that runs once per test file. The setup file starts an OTLP receiver on a free port, over both HTTP and gRPC, and writes the following variables into `process.env`. A child process started from the test inherits them, so a CLI or a server spawned by the test exports to the same receiver.

| Variable                                                                                                        | Value                                                                                           |
| --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `OTEL_EXPORTER_OTLP_ENDPOINT`                                                                                   | The receiver's HTTP endpoint, or its gRPC endpoint when `OTEL_EXPORTER_OTLP_PROTOCOL` is `grpc` |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`, `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` | Empty, so that test telemetry never reaches a real collector                                    |
| `OTEL_TRACES_EXPORTER`, `OTEL_METRICS_EXPORTER`, `OTEL_LOGS_EXPORTER`                                           | `otlp`                                                                                          |
| `OTEL_BSP_SCHEDULE_DELAY`, `OTEL_BLRP_SCHEDULE_DELAY`                                                           | `50`, unless already set                                                                        |
| `OTEL_METRIC_EXPORT_INTERVAL`, `OTEL_METRIC_EXPORT_TIMEOUT`                                                     | `100`, unless already set                                                                       |

The short delays matter more than they look. The OpenTelemetry specification sets the default delay of the batch span processor to 5,000 ms[^otel-env]. With that default, a test that waits 5 seconds for one span fails, because the batch has not been sent yet. I ran exactly that test with `OTEL_BSP_SCHEDULE_DELAY=5000`, and it failed with `Expected 1 spans within 5s, received 0 matching of 0.`

The receiver reads protobuf and JSON, gzip-compressed or not, and decodes protobuf with code generated by protobuf-es from opentelemetry-proto v1.11.1. It does not use a mock collector package or a Docker container.

## A test waits for what it expects

`waitForSpans`, `waitForLogs` and `waitForMetrics` poll the receiver every 20 ms until the given number of matching items arrive, and fail after 5 seconds by default. Each takes `where`, `count`, `timeout` and `interval`. The functions return Effect values, and `effect` is a peer dependency so that the test and the plugin share one copy of Effect.

```ts
import { NodeSDK } from "@opentelemetry/sdk-node";
import { waitForSpans } from "@r_masseater/vitest-otlp";
import { Effect } from "effect";
import { expect, test } from "vite-plus/test";

test("checkout is traced", () =>
  Effect.gen(function* () {
    const sdk = new NodeSDK();
    sdk.start();
    yield* checkout;
    yield* Effect.promise(() => sdk.shutdown());

    const spans = yield* waitForSpans({
      where: (span) => span.name === "checkout",
    });
    expect(spans).toMatchObject([{ attributes: { "order.id": "o-1" } }]);
  }).pipe(Effect.runPromise));
```

`NodeSDK` above takes no options. It reads the endpoint and the exporters from the environment that the setup file wrote, which is what the test proves to work. `clearTelemetry` empties the receiver between cases in the same file.

## It adds about 60 ms to a test

I measured the cost on November 18, 2026, in a 4-core Linux container with Node.js 26.13.1. Starting the receiver took 1.3 to 2.3 ms and stopping it 0.7 to 2.9 ms over five runs. For the round trip, a test ended N spans without calling `shutdown` and measured the time until `waitForSpans` returned all of them, three times per N.

| Spans | Time until all were received |
| ----- | ---------------------------- |
| 1     | 61.0 to 69.4 ms              |
| 10    | 61.5 to 62.9 ms              |
| 100   | 62.9 to 64.6 ms              |
| 1,000 | 76.0 to 87.9 ms              |

Almost all of the time up to 100 spans is the 50 ms schedule delay plus one 20 ms polling interval. The package's own suite of 9 test files and 16 tests runs in 14.8 seconds, and 6.5 seconds of that are the two tests that start Weaver, described below.

## How it differs from other ways to test telemetry

The common alternative is an in-memory exporter, which keeps spans inside the process and never goes through OTLP. [autotel-vitest](https://jagreehal.github.io/autotel/testing/vitest/) also collects spans inside the process, giving each test its own parent span. Vitest's built-in [OpenTelemetry support](https://main.vitest.dev/guide/open-telemetry) traces the test run itself rather than the code under test.

| Approach                                      | Goes through OTLP | Child processes | Needs Docker |
| --------------------------------------------- | ----------------- | --------------- | ------------ |
| In-memory exporter                            | No                | No              | No           |
| autotel-vitest                                | No                | No              | No           |
| Collector container such as grafana/otel-lgtm | Yes               | Yes             | Yes          |
| vitest-otlp                                   | Yes               | Yes             | No           |

## Checking semantic conventions with Weaver

`otlp({ semconv: true })` also checks every received item against the OpenTelemetry semantic conventions. A global setup starts one [Weaver](https://github.com/open-telemetry/weaver) live-check, each receiver forwards what it receives to it over gRPC, and the run fails at the end when the report has a finding at or above `failOn`. The default registry is semantic-conventions v1.45.0, and the `weaver` binary must be on the `PATH`.

## Cloudflare Workers under Miniflare

`tailWorker()` from `@r_masseater/vitest-otlp/workers` returns a tail worker to pass to Miniflare's `streamingTails`. It converts each invocation of the Worker into OTLP protobuf and posts it to the receiver, so a test of a Worker waits for spans such as `kv_put` the same way.

```ts
import { waitForSpans } from "@r_masseater/vitest-otlp";
import { tailWorker } from "@r_masseater/vitest-otlp/workers";
import { Effect } from "effect";
import { Miniflare } from "miniflare";

test("caching writes to KV", () =>
  Effect.gen(function* () {
    const tail = yield* tailWorker();
    const miniflare = new Miniflare({
      workers: [
        {
          name: "app",
          scriptPath: "worker.js",
          kvNamespaces: ["CACHE"],
          streamingTails: [tail.name],
        },
        tail,
      ],
    });
    yield* Effect.promise(() => miniflare.dispatchFetch("http://localhost/"));
    yield* waitForSpans({ where: (span) => span.name === "kv_put" });
    yield* Effect.promise(() => miniflare.dispose());
  }).pipe(Effect.runPromise));
```

Locally, Miniflare does not report the Worker's script name to the tail, so `service.name` of these spans is `worker`.

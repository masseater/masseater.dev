複数のリポジトリを Claude のスレッドで並行して進めていたとき、取りまとめ役の Claude が各スレッドへ「テンプレートの変更は小さく分けて、先にマージして」と指示を出していた。僕はこう返した。

> 小さく先にマージすることに意味はないっす
>
> 根本をちゃんと解決してね

変更を小さく分けて早く main に入れるのは、長いあいだ良い習慣とされてきた。AI の書く PR が大きくなった今こそ小さく出すやり方を学び直すべきだ、という声もある。Pawel Brodzinski は、AI を多く使ったプロジェクトで PR の平均の大きさが 3.5 倍になったと数え、思っているより早く小さいバッチを学び直すと書いている[^brodzinski]。

僕は学び直す必要を感じていない。小さく出して得ていたものは、どれも人の手の遅さを前提にしていた。差分が小さければ人がレビューで読み切れるし、壊れたときに原因の候補が狭く、戻すのも楽になる。長く分かれたブランチを後から統合するときの衝突も減り、早く出せば早く反応が返る。読むのも、統合するのも、原因を探すのも人だったから、1回に扱う量を人の頭に収まる大きさまで削る必要があった。

今の僕の開発では、その手間を人が持っていない。PR の差分は[読んでいない](/blogs/stop-pr-review)し、衝突は Claude が base を取り込んで解消する。壊れたら Claude がログと差分から原因を探す。僕が確かめるのは main にマージされた後で、いくつものスレッドの成果をまとめて動かして見ている。そこへ一部だけを先に入れても、その一部を単独で見る人はいないので、早く分かることは何も無い。

先に入るのは、直した箇所だけがほかと違う挙動をする main だ。テンプレートの変更を1つのリポジトリにだけ入れれば、同じ足場を持つほかのリポジトリとずれる。最初の一片をマージした Claude は、その一片が通ったことを完了として報告する。スレッドは終わればコンテキストを失うので、残りの片を後から誰かが拾う保証も無い。小さく先に入れることは、前に進んだ感触を残したまま途中で止まるやり方になっていた。

変更の単位は、問題が1つ根本から片づいたかで決めたい。Claude が数千行を書いて verify が通るなら、数千行のまま入れればいい。差分の大きさが問題になるのは人が読むときで、読まないなら大きさで分ける理由も残らない。

このプロジェクトで Claude に渡している指示には「部分最適をしない。常に全体を俯瞰し、直した箇所だけが独立して他と違う挙動になる状態を作らない」と書いてある。mirucord の AGENTS.md には「部品だけを先に入れず、使う側と同じ PR にする」とある。

[^brodzinski]: [We 3.5x'd Our Pull Requests with AI: Now We Catch Fewer Bugs](https://brodzinski.com/2026/07/3x-pull-request-size-ai.html)

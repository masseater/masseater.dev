Claudeに、既に存在してうまく動作しているツールを次々と作り直させている。y8はmarkdownlintの代わりのMarkdownリンターである。fu4はactionlintとzizmorの代わりのGitHub Actionsリンター、h56mはBetterleaksとsecretlintの代わりのシークレットスキャナーだ。そしてmschは私の全リポジトリのチェックを1つのコマンドにまとめてくれる。11月7日、その理由をこう記した。「他人の OSS の更新フローに縛られず、全部自分で作って気になったら即直したい」。私が欲しいのは、AIがあらゆる計測を自力で行える場所であり、借り物のツールはその邪魔をし続けている。

| ---------------------------------------------------------------------- | -------------------------------------------------------- | -------------------------------------- | ------------------------------------------- |
| [y8](https://github.com/masseater/masseater.dev/tree/main/libs/y8)     | markdownlint, rumdl                                      | pulldown-cmark                         | markdownlint MD001～MD060                   |
| [fu4](https://github.com/masseater/masseater.dev/tree/main/libs/fu4)   | actionlint, zizmor                                       | zizmorの公開クレート、tree-sitter-bash | actionlint と zizmor のオフライン監査       |
| [h56m](https://github.com/masseater/masseater.dev/tree/main/libs/h56m) | Betterleaks, secretlint                                  | Kingfisherのマッチングエンジン         | Betterleaksのルールを、独自の形式で読み込む |
| [msch](https://github.com/masseater/masseater.dev/tree/main/libs/msch) | スキルで記述されたリポジトリごとのスクリプトおよびルール | 上記のツールとoxlint                   | なし；ルールは自作                          |

## ライブラリに合わせてコードを曲げる方が、書くよりもコストがかかる

私のルールは相変わらず、理由なくビルドやラップはせず、新しいものを書く前に既存のライブラリを探すことだ。11月15日、ひとつ例外を追加した。「一般的なライブラリを一般的な使い方するために無理やり合わせた結果効率下がったりすると本末転倒なので、もう自分のユースケースに合わせて独自ライブラリを作り込んで良いことにしてる」。

コストについては、置き換えたすべてのツールで顕在化した。markdownlint、actionlint、Betterleaksはそれぞれ独自のフォーマットで設定ファイルを読み込んでいたが、リポジトリ内の他のすべての設定は単一の `vite.config.ts` に収まっていた。actionlintはGoバイナリとして提供されているため、呼び出し元のTypeScriptと同じトレースにスパンを報告できない。GitHubがリポジトリ自体を参照する `uses: $/path` 構文を追加した際、actionlint 1.7.12はこれを拒否し、私側での唯一の対処法はリリースを待つか、この構文の使用を止めることだった。

## 元のツールのテストが仕様となる

Claudeがコードを記述し、元のツールがすでに「正しい」の意味を定義しているため、リビルドは今や低コストで実現できる。ここでのすべてのツールは、置き換え対象となるツールのテストデータを取り込んでおり、リリース前に同一の回答を提示しなければならない。y8は、436個のフィクスチャにおいてmarkdownlint 0.42.1の全53ルールに一致している。fu4はactionlintの指摘事項を同一のメッセージと位置で報告しており、またzizmorの43件のセキュリティ監査の移植版は、zizmor 1.32.0の全278件のスナップショットケースと一致している。

まず元のツールと一致させ、その後に変更することで、変更内容を意図した形に保てる。fu4がactionlintと異なる点は、私が選択した一点にある。それは、ワークフローで使用している `uses: $/path` を受け付けることだ。y8は速度が異なる。私のモノレポにある267個のMarkdownファイルにおいて、y8のリント処理時間は28 msであるのに対し、rumdlは70 msかかる。rumdlはすでにmarkdownlintをRustで書き直したものである。

## コアを借りて、サーフェスを構築する

仕様に準拠したパーサーやマッチングエンジンを再構築することはない。y8はpulldown-cmarkでパースし、fu4はzizmor自身のクレートでzizmorの監査を動かし、h56mはKingfisherのエンジンでシークレットを照合する。私がビルドするのは、実際に手を加える部分、つまり `vite.config.ts` の設定セクション、コマンド、診断、スパン、およびルールである。

ルールは同様にエンジンから分割される。各エンジンはOSごとにビルドされるRustパッケージであり、そのルールは `<engine>-presets` という1つのTypeScriptパッケージとして提供され、そこからリポジトリが対象ごとにプリセットを選択する。エンジンは構文木を共有メモリ経由でTypeScriptルールに渡し、計測値によってTypeScriptが遅すぎると判断された場合にのみ、ルールがRustに移行する。

## mschは私の修正内容をチェックに変換する

mschは、これらのツールと私自身のルールが合流する場所だ。リポジトリのあらゆるチェックを単一のコマンドで実行し、すべてのプッシュで実行される `vp run verify` の一部となっている。コードを説明するコメントや引数を転送するだけのラッパー関数など、Claudeの同じミスを2回指摘した場合、その指摘はスキル内の一文ではなく、mschチェックとなる。それ以来、Claudeはルールを、スキップしてよいテキストではなく、失敗時のチェックとして認識するようになった。

mschが実行するすべてのツールを自分が管理しているため、新しいチェックが他人を待つことはない。y8やfu4でルールの修正が必要になった際、同じスレッドが1つのPRでツールとリポジトリを変更する。

# @masseater.dev/repository-ci

Vite+ tasks that the hourly cache job and main's verify job use to handle this repository's Actions caches, Issues for failed deploys, the set of stacks to deploy and their production deploys, and the zenn branch.

A stack counts as changed since its last deployment when a file under its packages or their workspace dependencies changed, or a shared file changed (`.github/actions/`, `patches/`, a root file other than Markdown, the lockfile and `pnpm-workspace.yaml`). `pnpm-lock.yaml` and `pnpm-workspace.yaml` are judged by what pnpm resolved instead: the lockfile at the last deployment and at HEAD are read with `@pnpm/lockfile.fs`, and the stack counts as changed only when the set of packages reachable from one of its importers differs, or when the lockfile's settings, overrides, patches or extensions differ. A bump of a root-only tool such as msch therefore deploys nothing. If either lockfile cannot be read, the stack counts as changed.

Main's deploy plans first. The `plan` job in `deploy.yml` runs `deploy-stacks`, which decides per stage (`deploy:bootstrap`, `deploy:tailnet`, `deploy:broker`, `deploy:zone`, `deploy:production`) which stacks changed since the stage's last recorded deployment. A stage job runs only when its list is not `[]`, and `record-stage` records the stacks it deployed under the `stages` environment (production keeps its own records). `deploy:github` is not planned: it also publishes the zenn branch, whose articles are not in the package's dependency closure, and it is off the critical path. Skipping a stage means a drift in what it manages, or a secret rotated in GitHub that a stage writes to Cloudflare, is corrected at the next change to that stage rather than at the next push. Dispatch `verify` on main to deploy every stage anyway (`FORCE`).

A hung deploy holds the `deploy` concurrency group, so every run behind it waits and only the newest pending run deploys. Keep each stage bounded: every job in `deploy.yml` has a `timeout-minutes` of about twice the longest duration measured on main over 24 runs on 2026-11-28 (production 7.1 minutes, bootstrap 6.9, tailnet 3.8, github 3.9, broker 2.2, zone 2.0), and `deploy-production` stops a stack after 10 minutes. A stopped command gets `SIGKILL` 10 seconds after `SIGTERM` (`forceKillAfter` in `@r_masseater/github-workflow` 0.1.1; before it, Effect waited for the exit without limit, which held production for 35 minutes). A stack that is still running after 7 minutes writes the process tree and open sockets to the job log and to the `deploy-hang` artifact. When a job ends by its timeout, raise its limit only after reading that artifact.

`prune-caches` keeps the newest entry of each kind on main (one pnpm store, one task cache, one lint decision cache, one per shard for the msch results, one per package for the daily persisted data) and deletes every entry on other refs and the retired `vite-plus-` entries. The hourly `cache` workflow runs it after it saves the pnpm store. `.github/actions/setup` restores the newest `pnpm-store-` entry whatever lockfile it was saved for, and only the `cache` workflow saves one, so a lockfile change on main never adds an entry per push. The task cache works the same way: every job restores the newest `vite-task-` entry and only the `cache` workflow, which runs every task, saves one.
